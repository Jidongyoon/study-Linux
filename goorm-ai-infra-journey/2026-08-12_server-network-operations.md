# 🖥️ 서버 초기 구성 · 서비스 운영 · 네트워크 장애 분석

> 2026-08-12 학습 기록

## 1. 빈 서버에서 웹 서비스 구성

오늘은 빈 서버에서 `web02` 서비스를 직접 구성했다.

### 서비스 계정과 디렉터리

서비스 전용 계정과 디렉터리를 만들고 소유권과 권한을 설정했다.

    sudo mkdir -p /srv/web02
    sudo chown web02:web02 /srv/web02
    sudo chmod 755 /srv/web02
    ls -ld /srv/web02

서비스를 전용 계정으로 분리하면 서비스가 root 권한으로 실행되는 것을 피할 수 있다.

---

## 2. 환경변수

Python 애플리케이션의 설정값을 환경변수로 분리했다.

    APP_PORT=8002
    APP_NAME=web02
    APP_ENV=prod

환경변수는 프로그램의 코드와 설정을 분리해서 실행 환경에 따라 다른 값을 전달하기 위한 방법이다.

오늘은 우선

> "환경에 따라 설정값을 다르게 주는 것"

이라는 개념을 이해하는 데 집중했다.

---

## 3. systemd로 서비스 관리

Python 웹 애플리케이션을 systemd 서비스로 등록했다.

서비스 파일을 변경한 후:

    sudo systemctl daemon-reload

서비스 실행:

    sudo systemctl enable --now web02

상태 확인:

    systemctl status web02

서비스가 정상적으로 실행되었는지 확인하고 실제 Port까지 확인했다.

    sudo ss -tlnp | grep ':8002'

최종적으로 `0.0.0.0:8002`에서 Python 프로세스가 LISTEN 중인 것을 확인했다.

---

## 4. 서비스 장애 원인 확인

서비스가 정상적으로 시작되지 않는 상황에서 바로 설정을 바꾸지 않고 로그부터 확인했다.

    sudo journalctl -u web02

`Address already in use` 오류를 확인했고, Port를 누가 사용하고 있는지 확인했다.

    sudo ss -tlnp | grep ':8002'

이후 PID를 확인하여 실제 프로세스를 조사했다.

    ps -fp <PID>

오늘 배운 장애 분석 흐름:

    서비스 상태
    → journalctl
    → Port 확인
    → PID 확인
    → 프로세스 확인
    → 원인 판단

즉, 오류 메시지를 보고 추측하기보다 로그와 현재 상태를 이용해 원인을 좁혀가는 것이 중요했다.

---

## 5. 서버 설정 자동화

오늘 수동으로 했던 서버 초기 설정을 Shell Script로 자동화했다.

    sudo chmod +x ~/setup_web02.sh
    ~/setup_web02.sh

스크립트에서 계정, 서비스 디렉터리, 환경변수, systemd 설정 등을 한 번에 구성하고 서비스가 정상적으로 실행되는 것까지 확인했다.

자동화의 핵심은:

> 같은 서버를 다시 구성해야 할 때 동일한 작업을 반복하지 않고 스크립트로 재현할 수 있다는 것이다.

# 🌐 6. 네트워크 장애 분석 실습

개인 실습으로 접속 실패 상황을 직접 만들고 원인을 구간별로 좁혀보았다.

    애플리케이션
    → Port
    → IP 통신
    → 이름 해석
    → 방화벽 / 외부 연결

## 7. 애플리케이션 확인

Python 테스트 서버를 실행하고 직접 접속했다.

    python3 -m http.server 18080 --bind 0.0.0.0
    curl http://10.0.2.15:18080

정상 응답이 확인되면 애플리케이션 자체의 문제를 배제할 수 있다.

---

## 8. Port와 IP 확인

Port가 실제로 열려 있는지 확인했다.

    sudo ss -tlnp | grep ':18080'

IP까지 통신이 가능한지도 확인했다.

    ping -c 4 10.0.2.15

각 단계에서 정상임을 확인하면서 문제의 범위를 계속 좁혀갔다.

---

## 9. DNS 장애 만들기 및 해결

`web-practice.local`이라는 이름을 만들고 잘못된 IP를 연결하여 이름 해석 문제를 발생시켰다.

    getent ahostsv4 web-practice.local

잘못된 IP가 반환되는 것을 확인한 후 `/etc/hosts`의 IP를 실제 서버 IP로 수정했다.

    10.0.2.15 web-practice.local

다시 이름 해석을 확인하여 정상적인 IP가 반환되는 것을 확인했다.

최종 원인:

> 서비스와 Port, IP 통신은 정상이었지만 `web-practice.local`이 잘못된 IP로 해석되어 접속이 실패한 것이 원인이었다.

## 10. 오늘의 핵심

오늘은 단순히 명령어를 외우기보다 **서버를 구성하고 문제가 생겼을 때 어디부터 확인해야 하는지**를 실습했다.

### 서버 운영

    계정
    → 디렉터리 / 권한
    → 환경변수
    → systemd
    → Port
    → 로그

### 장애 분석

    가장 가까운 곳부터 확인
    → 정상인 부분을 배제
    → 문제 구간을 좁힘
    → 원인을 확인
    → 수정
    → 다시 정상 여부 확인

오늘 가장 중요하게 배운 것은

> **장애가 발생했을 때 바로 설정을 바꾸는 것이 아니라, 정상인 구간을 하나씩 배제하면서 문제의 위치를 찾아가는 것이다.**
