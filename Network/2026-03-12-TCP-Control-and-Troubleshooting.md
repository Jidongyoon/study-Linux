Network Deep Dive: TCP Control & Troubleshooting (2026-03-12)
Key Concept: TCP는 단순한 연결을 넘어, 네트워크의 신뢰성과 효율성을 보장하기 위해 끊임없이 상태를 감지하고 스스로 조절하는 '지능적인 고속도로 관리자'와 같다.

1. TCP의 3대 핵심 제어 메커니즘
🛠️ 오류 제어 (Error Control)
데이터가 유실되거나 손상되었을 때 이를 복구하여 신뢰성을 보장합니다.

재전송 (Retransmission): ACK가 오지 않거나 타임아웃 발생 시 패킷을 다시 전송합니다.

SACK (Selective ACK): 유실된 특정 패킷만 골라서 재전송을 요청하여 효율을 높입니다.

🌊 흐름 제어 (Flow Control)
송신자와 수신자의 속도 차이를 조절하여 수신자의 버퍼가 넘치지 않게 보호합니다.

슬라이딩 윈도우 (Sliding Window): 수신자가 처리할 수 있는 양(RWND)만큼만 데이터를 보냅니다.

🚦 혼잡 제어 (Congestion Control)
네트워크 전체의 혼잡도를 판단하여 전송량을 조절함으로써 네트워크 붕괴를 막습니다.

느린 시작 (Slow Start): 전송량을 기하급수적으로 늘리며 대역폭을 탐색합니다.

혼잡 회피 (Congestion Avoidance): 임계치(ssthresh) 도달 후 선형적으로 전송량을 늘립니다.

빠른 재전송/회복: 3개의 중복 ACK 수신 시 문제가 있음을 직감하고 속도를 조절하여 빠르게 복구합니다.

2. ECN (Explicit Congestion Notification: 명시적 혼잡 통보)
패킷 유실이 발생하기 전에 네트워크 장비(라우터 등)가 직접 혼잡 상태를 알려주는 고급 기술입니다.

원리: 라우터가 혼잡을 감지하면 IP 헤더의 ECN 비트를 체크하여 송신자에게 전달합니다.

장점: 패킷을 버리지 않고도 "곧 막힐 것 같으니 속도를 줄여라"라고 미리 알려주어 재전송으로 인한 낭비를 줄입니다.

효과: 응답 시간(Latency)이 중요한 실시간 서비스에서 매우 중요합니다.

3. TCP 트러블슈팅 상황 분석
실무에서 마주칠 수 있는 L4 계층의 주요 장애 상황과 판단 근거입니다.

❌ 상황 1: Connection Timeout (연결 수립 실패)
증상: SYN_SENT 상태만 지속되다가 연결 끊김.

원인: 하위 계층(L1~L3) 경로 단절, 혹은 중간 방화벽의 패킷 차단.

분석: "길이 끊겼거나 문이 잠겼는가?"를 먼저 확인해야 함.

⚠️ 상황 2: Retransmission Storm (재전송 폭풍)
증상: 연결은 되어 있으나 속도가 극도로 저하됨.

원인: 네트워크 혼잡으로 인한 패킷 유실 발생.

확인: ss -it 명령어로 retrans 수치와 rtt가 치솟는지 확인.

📉 상황 3: Low CWND (전송량 급감)
증상: 네트워크 대역폭은 충분한데 전송 속도가 나지 않음.

원인: 잦은 패킷 유실로 인해 혼잡 제어 알고리즘이 cwnd를 계속 낮게 유지함.

분석: ssthresh 값이 너무 낮게 잡혀 있지는 않은지, 혹은 회선 품질(L1) 자체에 문제가 없는지 조사.

💻 실무 명령어 Cheatsheet

# TCP 내부 혼잡 지표 상세 확인 (cwnd, ssthresh, rtt 등)
$ ss -it

# 현재 열려있는 포트와 연결된 프로세스 확인
$ sudo netstat -tplan

# 네트워크 경로 상의 지연 구간 확인
$ mtr [목적지_IP]

엔지니어의 노트
L4 트러블슈팅은 "데이터가 가느냐 마느냐"가 아니라 **"데이터가 얼마나 건강하게 가느냐"**를 진단하는 과정이다.

특히 ECN과 같은 명시적 통보는 현대적인 클라우드 환경에서 대규모 트래픽을 처리할 때 시스템의 안정성을 결정짓는 중요한 요소가 된다.
