[2026-02-26] 인프라 구축 및 트러블슈팅 통합 리포트
1. 🐳 배포 방식의 패러다임: "비닐 압축 도시락" (Docker)
전통적인 설치 방식의 한계를 어떻게 현대 기술이 해결했는지에 대한 고찰입니다.

수동 설치의 한계: 오라클 설치 시 겪었던 긴 대기 시간(게이지 7%의 압박)과 OS 환경에 따른 의존성(Dependency) 문제.

도커의 혁신 (Vacuum Sealing):

개념: 프로그램만 담는 게 아니라 실행에 필요한 '공기(환경 설정, 라이브러리)'까지 통째로 비닐 압축하여 패키징함.

효율성: 레이어(Layer) 방식을 사용하여 중복되는 용량을 획기적으로 줄이고, 어디서든 뜯기만 하면(실행) 즉시 동일하게 작동함.

실무 적용: 콜센터와 같이 다수의 클라이언트 환경을 1초 만에 "뿌려야" 하는 환경에서 필수적인 기술임을 이해함.

2. 🍔 웹 서비스의 심장: APM 삼각 편대 (Apache, PHP, MariaDB)
웹사이트가 단순히 화면을 보여주는 것을 넘어 어떻게 데이터를 요리하는지 정리했습니다.

Apache (홀 서빙): 손님의 HTTP 요청을 가장 먼저 받는 문지기. httpd 서비스로 구동됨.

PHP (주방장): 손님의 요청에 따라 데이터를 가공하고 요리하는 동적 연산 엔진.

MariaDB (식재료 창고/금고): 모든 데이터가 저장되는 곳.

Security Insight: root 대신 전용 유저(webUser)를 만들고 외부 접속 권한(%)을 부여하여 '금고 보안'과 '접근성'의 균형을 맞춤.

📡 3. 네트워크 통찰: Localhost vs. Real IP
가상 머신과 외부 장치 간의 통신 원리를 파헤쳤습니다.

Localhost (거울의 법칙): 127.0.0.1은 "거울 속의 나"를 부르는 약속. 외부 장치(스마트폰)에서 이 주소를 치면 서버가 아닌 자기 자신을 찾게 되어 접속이 불가능함.

Real IP (집 주소): 외부 장치에서는 반드시 서버의 실제 주소(192.168.111.100)를 입력해야 네트워크 경로(Routing)를 타고 서버에 도달함.

DNS의 역할: 숫자로 된 주소를 인간이 읽기 쉬운 이름(naver.com 등)으로 치환해 주는 '전화번호부'임을 인지함.

🛠️ 4. 주요 트러블슈팅 및 해결 (Main Issues)
Case A: "웹페이지는 뜨는데 파일 업로드가 안 돼요!"
원인: 디렉토리 소유권 불일치. root가 만든 폴더는 웹 서버 대리인인 apache가 건드릴 수 없음.

해결: chown -R apache.apache owncloud/

교훈: 리눅스에서 서비스가 정상 작동하려면 해당 프로세스 계정에 **'물리적인 열쇠(소유권)'**를 줘야 함.

Case B: "호스트 PC는 되는데 스마트폰 접속은 왜 안 될까?"
원인: VMware NAT 모드의 한계. 가상 머신이 호스트 PC라는 보호막 안의 사설망에 숨어 있어 스마트폰(외부)에서는 보이지 않음.

해결책:

스마트폰을 동일한 Wi-Fi에 연결.

VM 설정을 Bridged 모드로 변경하여 공유기로부터 직접 IP 할당 유도.

리눅스 방화벽(firewalld)에서 80/tcp 포트가 열려 있는지 최종 확인.

🏆 오늘의 결론 (Summary)
"서버 구축은 단순히 명령어를 입력하는 과정이 아니라, 권한의 경계를 허물고(chown), 네트워크의 길을 뚫으며(Routing), 데이터를 안전하게 가두는(DB User) 정교한 설계 과정이다. 오늘 구축한 ownCloud는 단순한 저장소를 넘어, 인프라 전체 구조를 이해하는 훌륭한 교과서가 되었다."
